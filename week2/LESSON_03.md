# 第二周第三课：KV Cache 到底省了多少时间？

本课从“缓存写得对”进入“收益测得准”。目标不是跑出一个漂亮的加速倍数，而是能解释：省掉了哪些工作、还剩哪些工作、什么因素影响实际耗时。

建议分两次学习：先用 30–45 分钟设计实验，再用 60–90 分钟测量和解释。本文件是讲义与实验设计，benchmark_kv_cache.py 已准备，运行说明见 BENCHMARK_GUIDE.md。按你的要求暂不跑正式实验，当前没有实测性能结果。任务进度见 PLAN.md。

## 1. 先固定两个概念

上一课的条件：B=2、H=4、Dh=8，已有 6 个位置，再输入 2 个。

- 新 K/V 写入 [:, :, 6:8, :]。
- scores 形状是 [2,4,2,8]，不是 [2,4,2,6]。旧历史和本次新增的 K/V 都在其中。
- 因果性按位置判断：第七个 query 可以看第七个 key，但不能看第八个 key。不是“只有旧缓存才能被关注”。

上一轮评语里“8192 多算一倍”的小标题是笔误：你的 8192 字节答案正确。容量 16、FP32 时，本层预分配 KV 字节为 2×2×4×16×8×4=8192；reset 后有效字节为零，但预分配字节不变。

## 2. 本课比较的两条路径

沿用现有单层 MHA、随机 hidden states，不接 tokenizer、采样器或真实模型。不加入 SDPA、FlashAttention、CUDA Graph、torch.compile、分页缓存或多 GPU，以免同时改变多个因素。

设提示词长度为 L，随后处理 N 个新增输入位置。预先生成同一份 x，形状为 [B,L+N,C]，两条路径共用同一个 model。

| 阶段 | 完整重算 baseline | KV Cache 路径 |
|---|---|---|
| Prefill | 对 x[:, :L] 执行一次完整 MHA | 从空缓存开始，对 x[:, :L] 执行一次 forward_cached |
| 第 1 次增量步骤 | 重算 x[:, :L+1]，只取最后位置作为本步结果 | 只输入 x[:, L:L+1]，读取有效历史 K/V |
| 第 2 次增量步骤 | 重算 x[:, :L+2]，只取最后位置 | 只输入 x[:, L+1:L+2] |
| 第 N 次增量步骤 | 重算长度 L+N 的整个前缀 | 只输入第 L+N 个位置，最终 cache.length=L+N |

这里 N 表示预先给定的新增输入步骤，不是实际采样出来的输出 token 数。单层教学实验的耗时不能直接叫作真实服务的 TTFT 或 TPOT。

完整重算路径有意重复历史工作，这是本课要研究的 baseline；测出的倍数不能声称是相对 nano-vLLM 或 vLLM 的提升。

## 3. 先推导工作量，再猜速度

记 T 为某一步追加后的总长度，C=H×Dh，固定 B、H 和模型宽度。

| 工作 | 本课完整前缀重算 | 单 token 缓存步骤 |
|---|---|---|
| Q/K/V 投影 | 处理 T 个位置，约 O(BTC²) | 处理 1 个位置，约 O(BC²) |
| QKᵀ 与权重乘 V | 全部 query 对 key，约 O(BT²C) | 一个 query 对 T 个 key，约 O(BTC) |
| scores 张量 | [B,H,T,T] | [B,H,1,T] |
| 输出投影 | 处理 T 个位置 | 只处理新位置 |
| KV 管理 | 不保留跨步骤历史 | 写入新 K/V，保存并读取历史 K/V |

这些是当前 dense MHA 实现的数量级，不是精确 FLOPs，也不是运行时间预测。不能把 T 倍或 T² 直接当作实际加速倍数。

对固定步数 N，缓存仍要在每一步读取更长的有效历史。它避免了重复投影和历史输出重算，但没有把单步 Attention 变成与上下文长度无关。

短序列为什么未必明显加速？Python 调用、框架调度、GPU kernel 提交、mask 构造和 KV 写入仍存在；小矩阵还可能无法充分利用 GPU。上下文变长后，历史 KV 读取量也增长。究竟是提交、计算还是内存访问主导，需要证据，不能仅凭“decode 通常受带宽限制”给当前实验下结论。

## 4. 正确性必须在计时之前验证

用相同权重、相同 x、相同 dtype/device，在 model.eval() 和 torch.inference_mode() 下执行：

1. reset，比较完整 Prefill 与缓存 Prefill 的所有输出位置。
2. 对每个新增位置：用完整前缀重算作为基准，取最后一个位置，与单 token 缓存输出对拍。
3. 每步检查 cache.length，最终必须为 L+N。
4. FP32 初始使用 atol=1e-5、rtol=1e-4；若失败，先看误差和计算设置，不要为了通过测试任意放宽容差。

对拍、误差打印、.item() 和张量搬到 CPU 都放在正式计时之外。

## 5. 公平计时：每一轮从同一个起点出发

第一轮实验固定：B=2、C=64、H=4、dtype=FP32、N=16。只改变 L，先测 32、128，再扩展到 512、1024。模型、x、容量 L+N 的缓存预分配在计时外；缓存分配时间不包含在本次稳态计算延迟中，报告必须声明这一点。

下面是实验结构伪代码，不是可以直接运行的脚本：

```text
for 每个 L:
    固定随机种子，准备同一个模型和同一份输入
    验证两条路径逐步输出一致
    完整预热两条路径至少 3 轮，每轮缓存 reset → prefill → N 步
    正式重复至少 10 轮，交替 baseline/cache 的先后顺序

    baseline 每轮:
        单独计时：完整 Prefill
        单独计时：N 次逐渐增长的完整前缀重算

    cache 每轮:
        reset（不计时）
        单独计时：缓存 Prefill，包含投影、Attention 和 KV 写入
        单独计时：N 次单 token 缓存步骤，包含 append 开销

    保存各轮原始耗时；报告中位数和波动范围
```

缓存 Prefill 必须在 Decode 计时前完成，且不得重复计入 Decode。两边都把 Prefill 单列，不给任何一方“免费隐藏”它。预热结束后不能沿用已写满的缓存进入正式轮次。

不能为了让缓存更快，把新 token 的投影或 append 提前做完再开始计时；那测的已经不是同一范围的工作。

每轮记录：

- Prefill 毫秒。
- N 步 Decode 总毫秒。
- Decode 总毫秒 / N：这一段增长上下文上的平均每步耗时，不是固定长度 L 的单步耗时。
- Prefill + Decode：这一教学计算流程的总耗时，不包含请求排队、分词、采样和网络。
- Decode 加速比 = baseline Decode 时间 / cache Decode 时间；分别列清原始时间和统计口径。

不要用 Decode 加速比冒充全流程加速比，也不要把 batch 中 B 个位置混成 N×B 次模型调用。

## 6. GPU 异步计时：先测“等结果拿到手要多久”

主指标使用同步后的墙钟时间。测量区间采用如下结构：

```text
torch.cuda.synchronize()
start = time.perf_counter()
执行这一阶段的全部操作
torch.cuda.synchronize()
elapsed_ms = (time.perf_counter() - start) * 1000
```

这是计时方法示意，不是完整 benchmark。正式 Decode 主指标把 N 步放在一个测量区间里，别每步 synchronize：逐步同步会改变提交节奏，测出另一种工作负载。

CPU 版本无需 CUDA 同步，可验证流程，但 CPU 时间不能代替 L40 性能数据。

CUDA Events 可以作为后续辅助观察，测设备时间线上的区间；不要简单把墙钟时间减去 Events 时间就称作“纯 Python 开销”。主机提交与设备执行可能重叠，设备区间也可能有等待。

计时期间不开 profiler、不打印 explain、不重新生成输入；先确认所用 GPU 空闲，记录 GPU 编号、型号和负载情况。CUDA_VISIBLE_DEVICES=2 时，进程内部的 cuda:0 对应物理 GPU 2，不是 GPU 2 永远空闲。

同时记录 PyTorch/CUDA/GPU、实际 dtype、TF32 设置、B/C/H、种子、预热次数、重复次数、计时方法和每轮原始数据。数值表报告中位数，可另列 min/max 辅助看波动；10 轮数据不适合冒充可靠的服务尾延迟统计。

如果观察到下列现象，先把解释写成假设，再验证：

- 短序列几乎不加速：是否主要是提交开销、小矩阵利用率或缓存管理开销？
- 长序列重算明显变慢：是否出现了 T×T 的分数矩阵和更大的矩阵乘法？
- 缓存 Decode 也随 L 增长：是否与需要读取更多历史 K/V、计算更长 scores 一致？
- 缓存 Prefill 更慢：是否有额外写入、分配或掩码实现差异？

必要时再单独对一个短 L 和一个长 L 开 profiler，观察 CPU/CUDA 时间线、算子形状及 kernel 间隔。profiler 的耗时不能替代无 profiler 的正式性能表。某个算子时间长也不直接证明带宽瓶颈；如果证据不足，报告“待验证”。
